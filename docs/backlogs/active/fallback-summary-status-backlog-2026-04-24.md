# Fallback Summary Status Backlog

Updated: 2026-04-24
Status: Active

Activation note:

- drafted after fixing exact same-range summary regeneration so fallback rows no
  longer need to be treated as a regeneration blocker
- activated after the ATR ID-contract backlog closed and the active queue became
  empty
- keep the scope narrow: expose fallback summary quality state without adding
  hidden BYOK retries or changing prompt assembly behavior

This document is the backlog for making fallback summary rows visible as a
current quality state while keeping the prompt path simple and cost-safe.

It answers one narrow question:

- how should the system represent "this summary row currently contains fallback
  content" without changing memory assembly semantics or spending user API keys
  in the background

It is not:

- permission to automatically retry failed summary generation
- a broader summary quality-scoring system
- a replacement for exact same-range regeneration
- a reason to exclude fallback rows from prompt context
- a new memory mode

## Contract

`summary_status` describes the current contents of a `chat_summaries` row, not a
historical event.

Draft state values:

- `ok`: the row currently contains a successful model-generated summary
- `fallback`: the row currently contains locally generated fallback content

Prompt assembly should continue to treat both states the same in v0. A fallback
summary is still part of the best available conversation continuity. The status
is for product visibility, diagnostics, and explicit user-triggered
regeneration, not for filtering context.

Automatic retry remains out of scope. In a BYOK flow, background retries can
spend the user's provider quota without an explicit action, so v0 must not use
`summary_status = 'fallback'` as an automatic retry queue.

## Recommended DB Shape

Prefer a text column with a check constraint for the first implementation rather
than a Postgres enum.

```sql
alter table public.chat_summaries
  add column summary_status text not null default 'ok',
  add constraint chat_summaries_summary_status_check
    check (summary_status in ('ok', 'fallback'));
```

Reasons:

- it is easy to add in one migration
- existing rows become `ok` without a backfill script
- it leaves room for later values without enum migration friction
- it is still constrained enough to avoid ambiguous status strings

Do not add reason codes in v0 unless implementation needs them for a specific
UI or diagnostic surface. If reason codes are added later, keep them secondary
to the current state.

## Working Rules

- Store fallback content durably when summary generation fails, as today.
- Mark rows as `fallback` only when the persisted `summary` is generated by the
  local fallback factory.
- Mark rows as `ok` whenever a model-generated summary is successfully persisted
  for that exact row range.
- Preserve exact same-range update behavior for `chat_id + level + start_seq +
end_seq`.
- Keep malformed or partial overlaps as errors.
- Do not filter fallback rows out of `buildChatContext` or ATR source-map
  loading in v0.
- Do not schedule automatic retry from `summary_status = 'fallback'`.

## Why This Queue Exists

Fallback summaries currently preserve continuity after provider failures, empty
outputs, or max-token failures, but they are indistinguishable from successful
model summaries once persisted.

That creates three problems:

- users cannot tell when a summary panel is showing a locally compressed fallback
- operators cannot distinguish "normal summary exists" from "summary exists
  because the model path failed"
- future retry logic becomes tempting, even though automatic BYOK retries cross
  a cost and trust boundary

The goal is visibility, not automation. The row should say what it currently is,
and explicit regeneration should remain the way to replace fallback content with
an `ok` summary.

## Deferred For Later

- reason codes such as `provider_error`, `empty_output`, or `max_tokens`
- fallback age or first-seen timestamps
- operator metrics for fallback frequency by provider/model
- opt-in automatic retry controls with clear BYOK cost disclosure
- richer summary quality states beyond `ok` and `fallback`

## End Condition

Stop when `chat_summaries` can represent whether each row currently contains
fallback content, prompt assembly remains behaviorally unchanged, and replacing
a fallback row requires an explicit regeneration path rather than a hidden retry.
